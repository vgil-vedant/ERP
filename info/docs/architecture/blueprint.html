PLATE 2

One submission, accepted

The write-through runs in two phases: the row is reserved locally first — which is also what allocates its reference number — then handed to the ERP. Only after the ERP answers is the local row stamped and the ledger written.

  1. POST /public/grievanceForm fields arrive. The session cookie, if present, identifies the person.
  2. validateRequired fields, max lengths, the arithmetic challenge that stands in for a CAPTCHA, and the cascade check — a child value must belong to its chosen parent, enforced server-side.
  3. INSERT INTO submissionThe row is written first. The reference number is derived from the id the database just handed out, so it cannot collide.
  4. id 57, reference GRV-000069Field values are flattened into submission_field at the same time. Anything matching pass|pwd|secret|otp|pin|captcha|token|cvv|challenge is dropped before it is ever persisted.
  5. POST /api/intakeSource system, source reference, the person, and the field list — over HTTP, to a separate process.
  6. upsert citizen, INSERT intakeThe citizen is created on first sight and refreshed after. The record is unique on (source_system, source_reference), so a retry never duplicates it.
  7. intake idField values land in intake_field.
  8. 201 { intakeRef: ERP-0000068 }Or 200 with duplicate: true if this exact record was already received.
  9. UPDATE + ledger + auditsubmission.erp_intake_ref is stamped, erp_sync records the attempt as synced, and audit_log takes a CREATE entry.
  10. 200 — both references shownThe visitor sees the portal's own reference and the ERP's, side by side.
PLATE 3

One submission, refused

If the ERP will not take the record, the local row is taken back out. The data row disappears; the audit entry does not, because audit_log rejects DELETE.

  1. POST /api/intake failsUnreachable, timed out after 5s, or answered 400/500.
  2. DELETE FROM submissionThe reserved row goes back out; submission_field cascades with it.
  3. erp_sync status 'failed' · audit_log action 'ROLLBACK'The ledger keeps the HTTP status and the message. The audit entry is permanent — the triggers abort any DELETE against it.
  4. 503 with the reasonThe page names the failure and says nothing was saved on either side.
Measured, not assumed. tests/e2e/test-rollback.sh stops the ERP, submits, and reads both files: 10 checks, 0 failures. The ledger currently holds 68 synced and 8 failed attempts — the 8 are these deliberate rollbacks.
