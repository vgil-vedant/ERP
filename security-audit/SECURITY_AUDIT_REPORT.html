Application Security Audit Report

EkSetu (Unified Records): Web Application, Integration Bus and Deployment Assessment
Report version: 1.0Assessment date: 21 November 2026
Environment: local development host and its Docker deployment (read-only)
Prepared by: AI-assisted application security review (Claude, Anthropic), for the project owner
Classification: Confidential. Contains no credentials, tokens or personal data.

Abstract

This report presents a source-level and configuration-level security assessment of the EkSetu (Unified Records) application: a Node.js 18 / Express back end with a React front end, a hub, five replicated government-portal front ends, per-department SQLite offices, an integration bus into a separate ERP service, a PostgreSQL database, and a Caddy edge proxy. The assessment was non-destructive. It combined code review, live read-only requests against the local deployment, the project's own 105-check security regression suite (all passed), and Gitleaks, Trivy and npm audit scans. 41 controls were evaluated: 17 passed, 11 partially, 5 failed, 5 are not implemented and 3 were not tested. 18 findings are reported: no critical, 1 high, 5 medium, 9 low and 3 informational. The code base shows deliberate security engineering (no built-in secrets, salted password hashes, hashed session tokens, origin checks, security headers, hardened containers). The most important weaknesses are in deployment rather than in the code: the site is served over plain HTTP on public and LAN addresses, the administrator login is reachable from any address, database backups are tracked in Git, and the database credential and runtime versions are weak or end-of-life. We recommend enabling TLS first, then restricting access, purging the backups, and rotating the database credential.

Keywords: application security, OWASP, transport security, secrets management, container hardening, dependency scanning.

1. Introduction

EkSetu is a local demonstration platform that brings records from five department systems (UIDAI, CCTNS, e-Forensics, eCourts and ePrisons) into one hub. It handles identity-linked records, so a weakness could expose personal data even though the data in this deployment is described as demonstration data. The project owner asked for an evidence-based audit of the real code base and deployment, to be reported without changing anything.

The objectives were to document the actual architecture and attack surface, to verify each security control instead of assuming it works, to classify what was found by severity, and to give remediation steps that can be retested. Section 2 describes the architecture, Section 3 the threat model, Section 4 the method, Section 5 the results, Section 6 the tooling gaps, Section 7 the risk analysis, Section 8 the remediation plan, Section 9 the limitations, and Section 10 the conclusion. The assessment follows the OWASP Top 10 [1] and the Application Security Verification Standard [2] as guidance.

2. Application Architecture and Attack Surface

Two Node.js 18 services run in hardened containers behind a Caddy edge proxy (Figure 1). The platform service is one Express process that listens on six ports: the hub on 4100 and the five portal replicas on 4173 and 4175 to 4178. It owns a SQLite database for citizen accounts and one SQLite database per department office. The ERP service on port 4200 serves the console, the lookup API and the integration-bus ingest endpoint. PostgreSQL 16 is attached to the same private Docker network. Secrets are Docker secrets read from files at start-up.

Requests move as shown in Figure 2. A citizen or officer posts to a portal, the record is saved in that department's own database, and an outbox sends it to the ERP in HMAC-signed batches. The ERP resolves identity by Aadhaar-first matching, stores Aadhaar numbers only as keyed hashes in its lookup mirror, and the hub administrator can reveal a number through an audited call that reads it from the UIDAI replica.

Figure 3 lists what is reachable from where, as observed on the running stack. The edge publishes the hub and portals on six public ports; the platform container also publishes the same services on the host LAN address; the ERP console and PostgreSQL are bound to the loopback address only. The edge hides the internal diagnostics path.

3. Threat Model and Assessment Scope

Assets. The administrator session; officer and citizen credentials; identity-linked records and Aadhaar-derived identifiers; the integration secret and lookup pepper; the databases and their backups.

Entry points and attackers. (a) An anonymous Internet or LAN visitor reaching the edge and the portals; (b) a registered citizen; (c) an officer of one department; (d) a network observer on the path to the HTTP-only edge; (e) a local user or container on the host; (f) anyone with read access to the Git repository.

Scope. The repository at the project root (back end, front end, tests, Docker and edge configuration, CI) and the locally running containers. Excluded: the genuine government sites that the replicas imitate (the application never contacts them), other projects on the same host, denial-of-service and load testing, destructive payloads, and any modification of code, data or configuration. Third-party systems were not tested.

4. Security Assessment Methodology

Passive analysis came first. We read the authentication, session, security-helper, integration and database-access code, the Docker, edge and CI configuration, and the dependency manifests. Live checks were read-only: response headers, unauthenticated access to API routes, and the visibility of internal paths, against the local deployment. The project's own security suite starts temporary copies on unused ports with temporary databases; it reported 105 passed and 0 failed.

Tools run in this audit were Gitleaks 8.30.1 [13] (history and working tree, matches redacted), Trivy 0.76.2 [12] (lockfiles, configuration, three images) and npm audit. They were downloaded into a scratch folder outside the project. Semgrep, OWASP ZAP, Checkov and testssl.sh were not run (Section 6). Secret files were inspected by file metadata only; their contents were never read, and no password hash was decoded.

Classification. Findings are Confirmed (verified in code, configuration or live responses), Scanner-reported (a tool reported it; reachability not verified) or Observation. Hypotheses are listed separately and never counted. Severity is the auditor's judgement of likelihood and impact on this deployment. CVSS 4.0 numeric scores were not computed: no validated calculator was available offline, and an unverified score would be an invented number. Each control was graded PASS, PARTIAL, FAIL, NOT IMPLEMENTED or NOT TESTED.

5.1 Authentication Security

Passwords are stored as salted scrypt hashes, session tokens are 256-bit random values and only a SHA-256 of each is kept, cookies are HttpOnly and SameSite, wrong-password responses are generic, and repeated failures return 429 (all verified by code and the security suite). The weaknesses are the single shared administrator without MFA (SA-07), the scrypt cost (SA-08), the registration disclosure (SA-09) and the short password rule (SA-10). A cookie-scope observation is SA-16. The Secure cookie flag depends on TLS (SA-01).

ERP-SA-07: Hub administrator authentication is a single shared account with per-address, in-memory throttling and no second factor Low

Status: Confirmed. Area: Authentication. CVSS 4.0: not scored (Section 4).

Location. backend/platform-api/src/services/hub-auth.js; backend/shared/admin-account.js

Explanation. There is one administrator account for the hub and the ERP console. Failed sign-ins are throttled per client address (8 in 10 minutes), the counter lives in memory and resets when the process restarts, sessions last 12 hours with no inactivity timeout, and no multi-factor option exists. The throttle does not slow an attacker who rotates addresses.

Evidence. hub-auth.js: limiter({ max: 8, windowMs: 10 min }), SESSION_HOURS = 12, sessions held in a Map; no MFA code path found.

Impact. With ERP-SA-01 and ERP-SA-02, a stolen or guessed password gives full administrative access with no second barrier and no individual accountability.

Prerequisites. Knowledge of the single password.

Recommendation. Add per-account lockout or exponential delay, an idle timeout, and TOTP or WebAuthn for the administrator; move to named accounts so audit entries identify a person.

Secure implementation.

// idle timeout: refresh `exp = now + 30 min` on each request, cap at 12 h absolute

Verification after remediation. Ten wrong passwords from different test addresses still slow the account; an idle session is rejected after the timeout; sign-in requires the second factor.

ERP-SA-08: scrypt cost parameter (N = 16384) is below the OWASP recommended minimum Low

Status: Confirmed. Area: Cryptography. CVSS 4.0: not scored (Section 4).

Location. backend/shared/security.js (SCRYPT = { N: 16384, r: 8, p: 1 }); backend/platform-api/src/db/index.js hashPassword()

Explanation. Passwords are hashed with salted scrypt, which is a sound choice, but the work factor is Node's default N = 2^14. The OWASP Password Storage Cheat Sheet lists N = 2^17 (with r = 8, p = 1) as the minimum configuration [3]. Citizen passwords use the Node defaults without any explicit cost.

Evidence. security.js line "const SCRYPT = { N: 16384, r: 8, p: 1 }"; db/index.js calls crypto.scryptSync(password, salt, 32) with defaults.

Impact. An attacker holding a leaked hash (for example through ERP-SA-03) can test guesses about eight times faster than at the recommended cost.

Prerequisites. Possession of a hash.

Recommendation. Raise N to 2^17 and store the parameters with each hash so existing hashes still verify and can be upgraded at next sign-in. maxmem must be raised accordingly.

Secure implementation.

crypto.scryptSync(pw, salt, 32, { N: 131072, r: 8, p: 1, maxmem: 256 * 1024 * 1024 })

Verification after remediation. New hashes carry the new parameters; a unit test verifies old and new hashes; sign-in latency stays acceptable.

ERP-SA-09: Citizen registration reveals whether an email address is already registered Low

Status: Confirmed. Area: Authentication. CVSS 4.0: not scored (Section 4).

Location. backend/platform-api/src/services/identity.js line 128

Explanation. Registering with an existing address returns "That email is already registered. Sign in instead." The sign-in form, by contrast, gives a generic message. Registration is limited to 10 per hour per address, which slows but does not prevent enumeration.

Evidence. Source line 128; sign-up limiter on line 60.

Impact. An attacker can learn which email addresses hold citizen accounts, aiding phishing and targeted guessing.

Prerequisites. Access to the registration form.

Recommendation. Respond identically whether or not the address exists and send the outcome by email, or accept the disclosure explicitly for this demonstration.

Secure implementation.

// always: 'If this address can be registered, we have sent a confirmation.'

Verification after remediation. Registering a known and an unknown address produce byte-identical responses and timing within noise.

ERP-SA-10: Citizen password policy is a minimum length of 8 only Low

Status: Confirmed. Area: Authentication. CVSS 4.0: not scored (Section 4).

Location. backend/platform-api/src/services/identity.js lines 80-84

Explanation. The only rules are 8 to 200 characters and a matching confirmation. NIST SP 800-63B [7] recommends screening new passwords against lists of commonly used and breached passwords. No password-reset flow was found among the reviewed routes.

Evidence. identity.js validateRegistration().

Impact. Weak but length-compliant passwords (for example "password1") are accepted.

Prerequisites. None.

Recommendation. Reject passwords on a common-password list (a local top-10,000 list is enough), keep the length minimum, and avoid composition rules.

Secure implementation.

if (COMMON.has(password.toLowerCase())) errors.password = 'Choose a less common password.';

Verification after remediation. Registration with a listed password is refused; a random 12-character password is accepted.

ERP-SA-16: Session cookies are scoped by host, not by port Informational

Status: Observation. Area: Session management. CVSS 4.0: not scored (Section 4).

Location. backend/shared/security.js cookie(); backend/platform-api/src/services/identity.js (header comment on cookies by host)

Explanation. Browsers send cookies to every port of the same host. The hub session cookie (hub_session) and the citizen cookie are therefore also sent to the portal ports on that host. The hub cookie is HttpOnly and its token is validated server-side, and all services are one process, so no exploitation path was found; it does mean the hub shares a cookie jar with five replica portals.

Evidence. Cookie attributes in code (Path=/, HttpOnly, SameSite=Lax); the identity module documents that cookies are not port-isolated.

Impact. Reduced isolation if a portal origin were ever compromised.

Prerequisites. A separate weakness in a portal origin.

Recommendation. Serve the hub on its own host name, or use the __Host- cookie prefix with Secure once TLS is in place.

Secure implementation.

Set-Cookie: __Host-hub_session=...; Secure; HttpOnly; SameSite=Lax; Path=/

Verification after remediation. The portal origins no longer receive the hub cookie in their request headers.

5.2 Authorization and Access Control

Every hub API route returned 401 without a session, the ERP console returned 401 without a token or Basic credentials, and the diagnostics path /__platform returned 404 through the edge. Cross-site form posts are refused by origin checks. The weakness is reach: the administrator login is open to every address (SA-02). Citizen-to-citizen object access and the ERP console's lack of an origin check are untested hypotheses (P-1, P-4).

ERP-SA-02: Administrator sign-in is reachable from any address; edge allowlist is unset Medium

Status: Confirmed. Area: Access control / Exposure. CVSS 4.0: not scored (Section 4).

Location. deploy/edge/Caddyfile @blocked matcher; deploy/edge/.state/ports.env (no EDGE_ALLOW entry)

Explanation. The edge supports an optional source-address allowlist (EDGE_ALLOW) but its default is 0.0.0.0/0 and the state file contains no EDGE_ALLOW value. The hub administrator login, the office (officer) logins and the citizen portals are therefore reachable from the whole Internet. The administrator account is a single shared account with no second factor (see ERP-SA-07).

Evidence. Caddyfile: "@blocked not remote_ip 127.0.0.1/32 {$EDGE_ALLOW:0.0.0.0/0 ::/0}"; ports.env lists EDGE_PORT_* and ERP_PUBLIC_PORT_MAP but no EDGE_ALLOW; the hub login page returned 200 on the edge port.

Impact. Widens the population able to attempt password guessing against the only administrator and the officer accounts; compounds ERP-SA-01 because credentials cross the Internet in clear text.

Prerequisites. Internet access to the edge ports.

Recommendation. Set EDGE_ALLOW to the office address ranges (or a VPN range) for the hub and office paths, keeping citizen-facing portals separate if they must stay public.

Secure implementation.

# deploy/edge/.state/ports.env
EDGE_ALLOW=203.0.113.0/24 198.51.100.17/32

Verification after remediation. From an address outside the allowlist the hub login returns 403; from an allowed address it returns 200.

5.3 Injection Vulnerabilities

No injection weakness was confirmed. Every SQL statement reviewed binds user values as parameters; the few statements built with template strings interpolate only constants such as table names or fixed JSON paths. First-party server code does not call the shell except one development seeding script. These are static-review results, not exploit attempts.

5.4 Cross-Site Security

The React views escape output, the hub and portals send a Content-Security-Policy, and clickjacking is blocked by frame headers. Only defence-in-depth gaps were found (SA-12).

ERP-SA-12: Output-encoding and Content-Security-Policy gaps (defence in depth) Low

Status: Confirmed. Area: Cross-site security. CVSS 4.0: not scored (Section 4).

Location. backend/platform-api/src/server.js (style-src 'unsafe-inline'); backend/erp-api/src/server.js (sec.headers() without csp); frontend/erp-console/views/dashboard.ejs lines 273-275; frontend/web/src/portals/behaviours.ts line 32

Explanation. (a) The hub and portal policies allow inline styles. (b) The ERP console sends no Content-Security-Policy [6]. (c) The legacy EJS console embeds JSON with <%- JSON.stringify(...) %> without escaping "<", unlike the other pages which escape it. (d) The portal cascading-select code builds option markup from server-supplied values without escaping the value attribute. In each case the data originates from server-controlled lists or counts, and no exploit was demonstrated; these are hardening gaps, not confirmed XSS.

Evidence. Source lines as listed; live headers from the hub login show the policy including style-src 'unsafe-inline'.

Impact. If a future change lets user-controlled text reach these sinks, script injection becomes possible with little further effort.

Prerequisites. A future data path to the sinks.

Recommendation. Escape "<" when embedding JSON, escape attribute values, add a CSP to the ERP console, and move inline styles to classes so unsafe-inline can be dropped.

Secure implementation.

const json = JSON.stringify(x).replace(/</g, '\\u003c');

Verification after remediation. A test payload containing </script> in a department name renders as text; the ERP console responds with a CSP header.

5.5 API Security

No cross-origin (CORS) headers are sent, request bodies are size-limited, and the API requires authentication except the signed ingest door. The ingest design is the finding (SA-11). GraphQL and WebSocket interfaces do not exist; the lookup page uses a server-sent event stream behind the same authentication.

ERP-SA-11: Integration-bus signing uses one shared secret, a time window only, and no throttle on failed signatures Low

Status: Confirmed. Area: API security. CVSS 4.0: not scored (Section 4).

Location. backend/erp-api/src/lookup/ingest.js verify(); backend/erp-api/src/auth.js (ingest door open)

Explanation. The ERP accepts POST /api/ingest/events without any other credential when the HMAC-SHA-256 signature and timestamp are valid. All five departments sign with the same secret, and the department name is taken from the request body, so any holder of the secret can speak for any department. The timestamp window is five minutes with no nonce, so a captured delivery can be replayed inside that window. Failed signatures are not counted by the sign-in throttle.

Evidence. verify() checks X-Integration-Timestamp within SKEW_MS = 5 minutes and the HMAC over "ts.body"; auth.js lets POST /api/ingest/events through before the throttle. Event idempotency was not tested independently.

Impact. Limited by the endpoint being bound to loopback in the observed deployment and by the secret being 48 bytes; if the secret leaks, forged department records can enter the lookup mirror.

Prerequisites. The shared integration secret, or a captured request within five minutes.

Recommendation. Use a distinct secret per department and bind the signed source to it, add a nonce or event-id replay cache, and count failed signatures per address.

Secure implementation.

const secret = SECRETS[source]; // one per department
if (seen.has(e.id)) return 'replay';

Verification after remediation. A delivery signed with department A's secret but claiming source B is refused; a replayed body is rejected; repeated bad signatures return 429.

5.6 File and Data Security

No file-upload feature was found, and static serving uses fixed maps or express.static. The data findings concern backups, retired keys and scanner noise (SA-03, SA-17, SA-18). SQLite and volumes are not encrypted at rest.

ERP-SA-03: Database backups and SQLite files are committed to the Git history Medium

Status: Confirmed. Area: Data protection / Secrets. CVSS 4.0: not scored (Section 4).

Location. backup/demo_replica_backup_20261028.dump; backup/sqlite-local-20261028/erp.sqlite; backup/sqlite-local-20261028/platform.sqlite (commit 2d0fe5d)

Explanation. Three database artefacts are tracked in Git even though .gitignore lists *.sqlite: a PostgreSQL custom-format dump (about 219 KB) and the two SQLite files (about 110 KB and 836 KB). The platform schema contains password_hash and password_salt columns. The artefacts are not encrypted. Their contents were deliberately not opened during this audit, so whether they hold real or synthetic personal data was not verified; the project describes the data as demonstration data.

Evidence. git ls-files lists the three paths; git log shows them in the initial commit 2d0fe5d; database/sqlite/platform/schema.sql defines password_hash / password_salt.

Impact. Anyone who can read the repository or any clone (including CI caches and forks) obtains the databases, offline-crackable credential hashes and any personal data they hold; history rewriting is required to remove them.

Prerequisites. Read access to the repository.

Recommendation. Remove the files from the repository, rewrite history (git filter-repo) after confirming with the repository owner, keep backups outside Git in encrypted storage, and extend .gitignore to backup/.

Secure implementation.

git filter-repo --path backup --invert-paths   # after agreement and a fresh clone
echo "backup/" >> .gitignore

Verification after remediation. git log --all -- backup returns nothing; gitleaks and trufflehog report no database files; backups restore from the encrypted store.

ERP-SA-17: Rotated secrets are retained as *.old files; secret files are mode 0644 inside a 0700 directory Informational

Status: Observation. Area: Secrets management. CVSS 4.0: not scored (Section 4).

Location. docker/.secrets/ (lookup_pepper.old, uidai_token_key.old; most other files 0644 owned by root)

Explanation. The rotation script keeps the previous LOOKUP_PEPPER and UIDAI_TOKEN_KEY as *.old files. The directory itself is mode 0700, which prevents other local users from reading the files, so the effective exposure is limited to the owner and root. Old keys remain usable for anything encrypted or hashed under them.

Evidence. ls -l metadata only; contents were not read.

Impact. Minor: extends the lifetime of retired key material.

Prerequisites. Local access as the owner or root.

Recommendation. Delete the *.old files once the rebuild of the lookup mirror is confirmed, and keep them in an encrypted vault if retention is required.

Secure implementation.

shred -u docker/.secrets/*.old

Verification after remediation. ls docker/.secrets shows no *.old files.

ERP-SA-18: Secret scanner reports are all in captured third-party site assets, none in first-party history Informational

Status: Observation. Area: Secrets management. CVSS 4.0: not scored (Section 4).

Location. backend/gov_replica/*/original_assets and reference_pages

Explanation. Gitleaks v8.30.1 [13] scanned 17 commits (about 427 MB) and reported 8,521 matches, all of them under the captured third-party site content (JWT-shaped strings and keys inside public JavaScript and HTML). Scanning the working tree reported 8,656, of which 176 fall outside the captured assets: crawl-analysis JSON in the same replica folders, runtime SQLite write-ahead files in database/ (ignored by Git), and the deliberately labelled test fixtures in tests/_test-secrets.js. No first-party credential was found in the commit history by this scan. This is a positive observation, not a vulnerability.

Evidence. gitleaks git --redact and gitleaks dir --redact reports; matches grouped by path prefix.

Impact. None directly; the volume of third-party matches will mask a real secret in future scans.

Prerequisites. n/a

Recommendation. Add a .gitleaks.toml that allowlists the captured-asset directories and test fixtures so that any new match is a real signal.

Secure implementation.

[allowlist]
paths = ['''backend/gov_replica/.*/(original_assets|reference_pages|analysis)/''', '''tests/_test-secrets.js''']

Verification after remediation. gitleaks reports 0 findings on a clean tree.

5.7 Business Logic Security

Not tested in this pass. The approval workflows, state transitions and race conditions in the department offices need dedicated test cases; replay of signed deliveries is hypothesis P-3.

5.8 Database Security

The database is bound to loopback and secrets come from files, but the credential is short and the application uses the superuser role (SA-04). Encryption at rest and connection TLS are not implemented (the link is inside a private Docker network).

ERP-SA-04: Weak, unrotated PostgreSQL credential, and the application connects as the database superuser Medium

Status: Confirmed. Area: Database security. CVSS 4.0: not scored (Section 4).

Location. docker/.secrets/pg_password (file metadata); compose.yaml postgres POSTGRES_USER and erp_api PGUSER

Explanation. The PostgreSQL password file is 9 bytes long and was last modified on 2026-10-28, whereas the other secrets are 48 bytes and were regenerated on 2026-11-20. The role named by POSTGRES_USER is created by the image as superuser, and the ERP API connects with that same role (PGUSER defaults to the same value), so a compromise of the API process yields full database control. The database port is bound to 127.0.0.1 only, which limits exposure. The password value itself was not read.

Evidence. ls -l: pg_password 9 bytes, dated Oct 28; other secret files 48 bytes, dated Nov 20; compose.yaml shows POSTGRES_USER and PGUSER both defaulting to the same name.

Impact. A short password is feasible to brute-force by anything that can reach 127.0.0.1:7432 (another local user, or a compromised container on the host); superuser rights remove any containment of SQL-level mistakes.

Prerequisites. Local or container-level access to the database port.

Recommendation. Generate a 32-byte random password, create a separate least-privilege application role (no superuser, no CREATEDB), and point erp_api at it.

Secure implementation.

CREATE ROLE erp_app LOGIN PASSWORD :'pw' NOSUPERUSER NOCREATEDB NOCREATEROLE;
GRANT CONNECT ON DATABASE demo_replica TO erp_app;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO erp_app;

Verification after remediation. SELECT rolsuper FROM pg_roles WHERE rolname = current_user returns false from the API; docker/make-secrets.sh output for pg_password is 32 bytes or more.

5.9 Infrastructure and Container Security

The application containers run as the unprivileged user "node" with a read-only file system, all capabilities dropped and no-new-privileges; the edge runs as a non-root user with capabilities dropped. The ERP console and PostgreSQL are not published beyond loopback. The weaknesses are the transport and exposure findings (SA-01) and the missing resource limits (SA-14). A firewall and SSH review needs root and was not done; the SSH daemon is listening on all interfaces and allows public-key login.

ERP-SA-01: Hub, portals and citizen sign-in are served over plain HTTP, including on public and LAN addresses High

Status: Confirmed. Area: Infrastructure / Transport. CVSS 4.0: not scored (Section 4).

Location. deploy/edge/Caddyfile (auto_https off); deploy/edge/compose.yaml (0.0.0.0:5011-5016); running container ERP_platform_api (LAN address :4100, :4173, :4175-4178); backend/shared/security.js cookie()

Explanation. The public edge (Caddy) is configured with auto_https off and serves the hub and the five portals over HTTP on all interfaces; the application container also publishes its ports on the host LAN address. No TLS is terminated anywhere, and no Strict-Transport-Security header is sent [8] because the code adds it only when req.secure is true. OWASP's transport-layer guidance [4] expects HTTPS everywhere. The session cookie is marked Secure only when the request itself arrived over HTTPS, so over HTTP it is sent without the Secure flag.

Evidence. Caddyfile line "auto_https off"; ss -ltn shows 0.0.0.0:5011-5016 listening; GET http://127.0.0.1:5011/login returned 200 over HTTP with no Strict-Transport-Security header; the project security suite itself asserts "the session cookie is not marked Secure over plain HTTP".

Impact. Anyone on the network path (public Internet hops, shared LAN) can read or alter traffic: the administrator password at /login, officer and citizen passwords, session cookies (session hijack) and the Aadhaar-linked records shown in the hub.

Prerequisites. Network position between a user and the server (same LAN, Wi-Fi, or an on-path ISP/router). No credentials needed.

Recommendation. Terminate TLS at the edge (a domain name with automatic certificates, or an internal CA for an IP-only site), redirect HTTP to HTTPS, enable HSTS, and stop publishing application ports on the LAN address (bind them to 127.0.0.1 so only the edge can reach them).

Secure implementation.

# deploy/edge/Caddyfile
{
  # remove: auto_https off
  email security@example.org

ERP-SA-14: No resource limits on any container; the database container is less hardened than the application containers Low

Status: Confirmed. Area: Container security. CVSS 4.0: not scored (Section 4).

Location. compose.yaml (hardening anchor; postgres service)

Explanation. The application services inherit a strong baseline (read-only root file system, all capabilities dropped, no-new-privileges, non-root user "node", in line with the CIS Docker Benchmark [14]), and the edge container is also non-root with capabilities dropped. None of the services sets memory, CPU or process limits, and the postgres service does not use the baseline (no read-only file system, capabilities not dropped).

Evidence. compose.yaml: x-hardening anchor has no mem_limit, cpus or pids_limit; postgres block lists only security_opt no-new-privileges.

Impact. A runaway or abused process can exhaust host memory or CPU and take down the other services, including the other applications sharing this host.

Prerequisites. Ability to trigger heavy requests; availability testing was out of scope.

Recommendation. Add mem_limit, cpus and pids_limit to each service, and apply cap_drop to postgres with only the capabilities its entrypoint needs.

Secure implementation.

services:
  platform_api:
    mem_limit: 768m
    cpus: 1.0
    pids_limit: 256

Verification after remediation. docker inspect shows the limits; the stack passes its health checks under the project test load.

7. Discussion and Risk Analysis

The confirmed findings are connected. Because the site is served over HTTP (SA-01) and open to every address (SA-02), the single administrator password (SA-07) crosses the network in clear text and can be guessed from anywhere; a captured session or password reaches the hub, which shows Aadhaar-linked records and can trigger an audited reveal. A leaked repository copy (SA-03) would give offline access to credential hashes that are cheaper to attack than recommended (SA-08), and the database credential (SA-04) would let a local foothold take the whole database. These are plausible paths, not demonstrated ones.

By contrast, the application code held up well against injection, redirect and cross-site request tests, and the project's suite guards many doors. The residual hypotheses are listed here and remain untested:

  1. P-1: ERP console state changes and cached Basic credentials. The ERP API has no Origin check (the hub and portals do). Browsers resend cached HTTP Basic credentials to the origin, so a cross-site form post to the console could carry them (see [5]). The only state-changing route reachable with Basic credentials found was the audited Aadhaar-reveal POST, and the port is bound to 127.0.0.1. Not tested.
  2. P-2: Client-address spoofing behind the edge. Rate limits key on req.ip, which trusts X-Forwarded-For only from the edge container. The Caddyfile states that client-supplied values are replaced. This was not tested with forged headers.
  3. P-3: Duplicate processing of a replayed delivery. Replays inside the five-minute window rely on the ERP treating repeated event identifiers as duplicates. The behaviour is described in the dashboard but was not tested independently.
  4. P-4: Citizen-account object access (IDOR). The citizen account pages were not exercised with two accounts, so horizontal access control between citizens is untested.

Priorities follow the chain: remove the network exposure first, then reduce what an intruder gains, then harden the code and process.

8. Remediation Strategy

Table 6 and Figure 7 set out the order. Each finding in Section 5 carries its own fix, example and retest step. Remediation was not started; it awaits the owner's approval.

Short-termSA-04, SA-05, SA-06, SA-07Platform and database ownersLeast-privilege DB role and new password; Node 22; rebuilt images; administrator MFA and lockout

  • Immediate. Terminate TLS and bind application ports to loopback (SA-01); set EDGE_ALLOW (SA-02); remove the backups from the repository and its history, with the owner's agreement (SA-03).
  • Short-term. New database password and a non-superuser application role (SA-04); Node 22 and rebuilt, re-scanned images (SA-05, SA-06); administrator MFA, lockout and idle timeout (SA-07).
  • Medium-term. Raise the scrypt cost with versioned hashes (SA-08); uniform registration responses and a common-password check (SA-09, SA-10); per-department signing keys and a replay cache (SA-11); encoding and CSP fixes (SA-12); container limits (SA-14).
  • Long-term. Security gates in CI (SA-15), dependency updates (SA-13), a Gitleaks allowlist (SA-18), retiring old keys (SA-17), monitoring and alerting, and a scheduled re-test. No finding is closed until it has been retested.

9. Limitations and Untested Areas

  • No active scanning, load or denial-of-service testing, and no exploitation, by design.
  • Semgrep could not be installed in this environment; the code review was manual and focused on authentication, sessions, SQL and output paths, not every file. OSV-Scanner could not parse the lockfiles here; npm audit and Trivy were used.
  • OWASP ZAP, Checkov, testssl.sh and Mozilla Observatory were not run; there is no TLS to test.
  • Host firewall, SSH password policy and operating-system patching need root access and were not tested.
  • Business-logic flaws, citizen-to-citizen access, and the ERP console's CSRF behaviour are untested.
  • The ERP image was not scanned separately from the platform image; the contents of backups and secrets were deliberately not read.
  • CVSS 4.0 scores were not computed (Section 4). The findings reflect the state on 21 November 2026.

10. Conclusion and Final Assessment

The application is better engineered than a typical demonstration project, and the audit found no critical or injection-class flaw. It is not ready for the public exposure it currently has: the transport is unencrypted, the administrator login is open to every address, and the repository contains database backups. We cannot declare the application secure, because large areas were untested and the review sampled the code rather than reading all of it. Fixing SA-01 to SA-04 would remove the most serious exposures; a retest should follow each change.
